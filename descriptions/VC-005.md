> 🏘️ **PropInsight** collects real-estate listing prices and turns them into
> clean, structured data. It deliberately does **not** decide what the numbers
> mean — it is the data layer, not a valuation product.

That narrow scope is the feature. Scrapers die by growing into analytics
products before they can reliably fetch a page. This one stops at the CSV.

## 🧩 The Common Schema

Every portal, however it publishes, normalizes to the same row:

| Field | Notes |
|---|---|
| `price` | Asking price, currency-normalized |
| `price_per_sqm` | Derived if absent |
| `location` | Locality + coordinates where available |
| `property_type` | Apartment, house, plot… |
| `area_sqm` | Units normalized on the way in |
| `rooms` | Typology |
| `condition` | New, used, for renovation |
| `listing_date` | First seen if the portal hides it |
| `url` | 🔑 provenance — every row traceable to its page |
| `fetched_at` | 🔑 provenance — when this was true |

> 💡 **Snapshots, not overwrites.** A listing appearing three times at three
> prices has been reduced twice. A listing that stops appearing has sold or
> been withdrawn. Price history falls out of repeated runs for free — no extra
> feature required.

## 🏗️ Why Site Profiles

Listing portals redesign often and without warning. If extraction lives in
code, every redesign is a development task.

```
  portals/idealista.yml   ─┐
  portals/imovirtual.yml  ─┼──►  one generic engine
  portals/remax.yml       ─┘
```

Adding a portal, or repairing one, is a config edit. **No new code.**

---

## 🌍 The Proxy Layer

Pluggable, because two real problems demand it:

1. 🚫 Large portals block whole datacenter IP ranges outright — politeness doesn't help
2. 🗺️ Many portals serve different prices, currency or inventory by visitor country — scraping a foreign market accurately means exiting from it

Supports per-request or sticky sessions, geo-targeting by country or city, and
automatic retry through another exit node. Commercial residential providers all
expose the same rotating endpoint, so they drop in as a config value.

> ⚠️ **Proxies are routing, not permission.** Rate limits, delays and
> concurrency caps apply **per target**, regardless of pool size — so adding
> proxies never increases the load any single portal sees.

## 🚧 Build Plan

| # | Stage | Done when |
|---|---|---|
| 1 | Common schema + CSV/JSON writers | A hand-made row exports correctly |
| 2 | HTTP fetcher + config-driven extraction | One portal yields clean rows |
| 3 | Site-profile format + first profile | A second portal needs no code |
| 4 | Playwright fallback | A JS-rendered portal works |
| 5 | Snapshot storage (SQLite) + price diffs | Run twice, see what changed |
| 6 | Politeness layer | robots.txt, delays, caps, cache |
| 7 | Proxy pool | Rotation, sticky, geo, failover |
| 8 | Scheduling + extraction-failure alerts | Silent breakage becomes loud |
| 9 | Cross-agency deduplication | One property listed thrice counts once |
| 10 | On-demand query mode | Serves single listings + comparables to **DealScope** (VC-011) |

## ⚠️ Risks

- 🛡️ Anti-scraping: rate limits, CAPTCHAs, IP blocks
- 🔧 Redesigns silently break selectors → **alerting on extraction failure is not optional**
- 💰 Residential proxies are a recurring per-GB cost, varying in quality and sourcing ethics
- 📜 Terms-of-service and data-reuse rules differ per site
- 🧹 Dirty source data: missing areas, mixed units, duplicates
- 👥 The same property relisted by several agencies inflates every count

---

## ✅ Definition of Done

Point it at a neighbourhood, run it weekly for three months, and get a CSV of
every listing with its full price history — each row traceable to the page and
moment it came from.

**Scope discipline:** it collects and normalizes. Judgement is VC-011's job.
