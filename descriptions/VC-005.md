PropInsight is a configurable web scraper whose single job is to collect real-estate listing prices and turn them into clean, structured data. It walks the result pages of a property portal, opens each listing, extracts a consistent set of fields — asking price, price per square metre, location, property type, area, number of rooms, condition, listing date and the listing URL — and writes them out as CSV, JSON, or straight into a database table. What it deliberately does not do is decide what the numbers mean: it is the data-collection layer, not a valuation product.

Each supported portal is described by a declarative site profile — a small config file that maps the portal's page structure to PropInsight's common schema, listing the search-results selector, the pagination rule, and a selector (or regex) per output field. Adding a new portal, or repairing one after a redesign, means editing that profile rather than writing new code, which matters because listing sites change their markup often and without warning. Simple, server-rendered sites are fetched over plain HTTP; sites that build their listings in JavaScript fall back to a headless browser automatically.

Scrapes are meant to be repeated, not run once. PropInsight stores every run as a timestamped snapshot rather than overwriting the previous result, so the history falls out of the data for free: a listing whose price appears three times at three different values has been reduced twice, and a listing that stops appearing has either sold or been withdrawn. Runs are idempotent and resumable — an interrupted scrape picks up where it stopped instead of starting the crawl again — and each row keeps the URL and fetch timestamp it came from so any figure can be traced back to its source page.

The output is intentionally boring and portable. A CSV drops into a spreadsheet, the JSON feeds a script or a notebook, and the SQLite/Postgres writer gives a queryable price history without any extra infrastructure. Typical uses: tracking asking prices in a specific neighbourhood over months before buying; building a personal dataset of comparable sales to sanity-check an agent's valuation; watching a fixed set of listings for price drops; or feeding a spreadsheet model or BI tool that expects tabular input.

Network egress is pluggable. Out of the box requests leave from the machine running the scrape, but PropInsight can also route them through a proxy pool — a handful of static proxies, a datacenter provider, or a commercial residential proxy service (Bright Data, Oxylabs, Smartproxy and similar all expose the same rotating HTTP/SOCKS endpoint, so they drop in as a config value rather than a code change). Residential exit nodes matter for two practical reasons: large portals routinely block whole datacenter IP ranges outright regardless of how slowly you crawl, and many listing sites serve different prices, currencies or inventory depending on the visitor's country, so scraping a foreign market accurately means exiting from it. The proxy layer supports per-request or per-session rotation, sticky sessions where a portal ties results to a session cookie, geo-targeting by country or city, and automatic retry through a different exit node when one gets blocked or times out.

It is built to scrape politely and stay on the right side of the sites it reads: it honours robots.txt, rate-limits itself with configurable delays and concurrency caps, identifies itself with a real user agent, and caches pages so that re-running a scrape during development does not mean re-hitting the server. The intended scope is personal research and small-scale market analysis — not bulk republication of someone else's listing database. Proxies are a routing tool, not a licence to hammer a site: rate limits, delays and concurrency caps apply per-target regardless of how many exit nodes are in the pool, so adding proxies never increases the load an individual portal sees.
